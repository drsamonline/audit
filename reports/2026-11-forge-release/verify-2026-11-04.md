# The fourteen invariants against the live estate — 4 November 2026

This is stage **R4** of [`05-release-plan.md`](05-release-plan.md), run a day early because the estate
moved under the plan. It is the first honest self-portrait of the estate against a fixed standard:
one row per invariant, one verdict, and the evidence for it.

Nothing here is a change. It is the measurement the release has to be judged against, and it is the
list the bootstrap's phase 6 will one day run automatically.

## The four live failures, with the one-line fix for each

| Workflow | Failing step | Root cause | Fix |
|---|---|---|---|
| `forge/new-app.yml` | Scaffold it, exactly as the manual path does | `GraphQL: Resource not accessible by personal access token (createRepository)` — `FANOUT_TOKEN` cannot create repositories | grant repository creation, or run this workflow on a token that has it. **Nothing in the estate builds until this is done**; the queue is stuck on `accent-oracle` since 2026-11-02 16:49 |
| `forge/health.yml` | Open or update the estate-failure issue | `GraphQL: Body cannot be blank (addComment)` — an empty report is posted as a blank body | if the report is empty, `exit 0` with a `::notice::`. A quiet fleet must be green |
| `forge/kit-audit.yml` | Drift — is a vendored copy actually out of date | `kit-drift could not read the API after 3 attempts` — installation token cannot read other repositories | point the step at `FANOUT_TOKEN` |
| `audit/licence-check.yml` | Check licence badges | `HCS` and `compfactory` have no LICENSE file; a badge would claim a licence the repo does not grant | add the two LICENSE files |

Three of the four are one-line changes. The first is an account action and it is the one that matters.

## What this changes in the release plan

1. **Phase 0 is not a formality.** It was written to print the plan tier and the token's scope. It
   now has a proven use: `createRepository` is exactly the kind of permission that is present in the
   design, absent from the token, and invisible until a workflow tries it two days later. Phase 0
   must attempt a *capability probe* per permission, not read a scope list.
2. **Invariant 8 needs a bumper, not just a pin.** A pin with nothing to bump it is a slower `@main`.
   The seed must ship a `build_pin` fixer in `sweep.py`, and phase 4 must write the *current* SHA,
   then re-check it on every run of `mode: verify`.
3. **Invariant 13 needs an owner.** Four cross-repo mechanisms exist and one of them holds a token
   with write on every repository while living in a profile page. The seed should ship a
   `cross-repo-mechanisms` check that enumerates every workflow holding a write-scoped PAT, by
   secret name, and fails when the list grows without a decision recorded against it.

Everything else in the plan stands. The eight phases, the manifest and the fourteen invariants are
unchanged; what changed is that four of them are now known to be broken in the estate the release
would be built from, which is precisely the argument for building it from invariants rather than
from a tarball of today.
